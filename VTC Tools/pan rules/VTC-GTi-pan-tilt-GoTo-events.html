The No-wait setting applies to GoTo.With PR1 or PR3 and the direction allowed, VTC uses continuous pan if it needs a correction and GoTo is not selected. From stopped, the pan error must exceed 1.5 × panToleranceMetres. Once moving, it can continue while the error exceeds panToleranceMetres.Example with tilt within tolerance: panToleranceMetres = 2 and acquisitionTriggerMetres = 5. Above 3 m and below 5 m starts continuous pan. At 5 m or more, GoTo is eligible. At 2 m or less, continuous pan stops. With acquisitionTriggerMetres = 0, an allowed pan correction above the tolerance is eligible for GoTo immediately. PR2 or PR4 holds pan.

Expected outcome in this example is from VTC’s perspective. An encoder reply gives position. In this proposal, VTC does not read GoTo acknowledgments or ask whether the axis has stopped.

REAL outcome shows the GTi response assumed in this scenario. VTC leaves Start replies unread. The scenario still needs a hardware test.

Outcome assumptions. The example assumes UDP packets arrive in order and that both rejected axes stay in motion throughout their respective bursts. GTi controller rows show what happens physically in the example. VTC only knows it sent the attempts and can use later encoder reads to observe position. If the motor stops between a rejected Set Target and the following Start, Start could use the previously stored target.

No-wait reversal. Send Stop without a reply wait. The 2-second reversal block is a timer and does not block the mount thread. Once it expires, use the latest GPS and send the opposite GoTo without a status request or command reply waits. The GTi can reject the target if pan is still moving. Routine encoder reads are the only socket waits in this reversal example. Times are illustrative.
