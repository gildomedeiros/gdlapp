## 1. Scope

Replace the visible **Export aiming log** action with a checked **Enable Full Log** menu item. Full logging automatically creates an accessible JSONL session file containing coordinates and diagnostics. OFF retains small private minimal logs, including packet gaps and invalid-data reasons. No export step is needed for full sessions.

The existing v2.4 target sources, packet acceptance, freshness, accuracy bypass, distance gate, yaw calculations, authority checks and pause/recovery remain. Single-row 48 dp footer, hidden compass and hidden map preview remain. No KML output is added in this release: JSONL includes route coordinates and diagnostic events in one file.

Earlier designs remain historical. Their statements that all logs omit coordinates, that routine diagnostics are always retained privately, or that the UI exports logs do not describe v2.5 Full Log.

## 2. UI and session lifecycle

- The overflow menu contains Details and **Enable Full Log**, checked when recording is requested/active. Full Log defaults OFF on process start; it is not a saved preference.
- ON schedules file creation immediately on the dedicated writer. It does not require Start aiming. A new filename is generated for each ON period.
- OFF immediately stops accepting new full records, then drains accepted records, writes session_end, flushes and closes the file. Minimal logging continues independently.
- The toggle is disabled while an open/close operation is pending. Menu state is refreshed when opened. Source selection may change during the recording under its existing OFF/STOPPED aiming-state restriction; source events and record types identify the selected input.
- Details includes the logging status, filename/path, storage error and cumulative dropped-record warning. Toasts acknowledge toggles and report storage errors. Opening is asynchronous: acknowledgement is not proof the file has successfully opened; Details reports the result.
- Leaving/pausing the flight screen stops its sources and closes Full Log with reason screen_closed, after the existing aiming cancellation. Returning does not automatically enable Full Log. This defines a foreground-screen recording session, not a background service.
- Process termination cannot guarantee session_end or clean close. Completed lines already flushed can remain; readers should tolerate a missing end record or an incomplete final line. Files are not deleted on normal close.
- On Android 7-9 only, public Downloads needs runtime storage permission. If missing, the toggle requests it; after granting, the user enables Full Log again. This avoids starting capture unexpectedly after a lifecycle-changing permission flow. Existing screen-pause aiming cancellation still applies.

## 3. Storage and file format

### Full files

Path shown in Files: **Downloads/CAM3**. Android MediaStore uses relative path `Download/CAM3/`.

Name: `cam3_full_yyyy-MM-dd_HHmmss_SSS_<8-character-UUID>.jsonl`.

Android 10+ uses MediaStore.Downloads with MIME application/x-ndjson; no broad storage permission is requested for this path. Android 7-9 uses the public Downloads directory and its existing manifest permission. Files remain visible while recording (not held as pending MediaStore items). Failure to open a newly inserted item attempts to remove that empty item. A later write failure preserves the partial file.

Each JSON line contains record (per-file number), timestamp (wall time with offset), epochMs, monoMs and event. Additional fields are typed JSON values. Non-finite numbers become null; strings escape controls, quotes, backslashes and surrogate code units. Event time is captured when enqueued, except start/end and overflow records generated by the writer. Record order reflects enqueue order; concurrent sources are not sorted after the fact.

| Event | Additional data |
|---|---|
| session_start / session_end | Version/format, or close reason |
| capture_source / target_source | Source at enable or later selection (target_source uses diagnostic detail) |
| lora_datagram | receivedAtMs, byteCount, rawBase64 of the exact datagram from the configured TTGO endpoint |
| lora_packet | receivedAtMs, sequence, senderMs, latitude, longitude, satellites, hdop, rssi, snr, receiverMissed, accepted and missingBefore |
| lora_gap | Diagnostic detail containing previous, received, missing, firstMissing and lastMissing |
| lora_rejected / lora_no_fix / lora_restart | Fixed rejection reason, NOFIX state or restart sequence |
| phone_fix | Latitude/longitude, fixElapsedMs, accuracyM, altitudeM, speedMps, bearingDegrees, acceptedBySource and mock |
| yaw_command | Actual submittedYawRate and aiming session ID, recorded after the existing SDK submission |
| readiness / blockers | Existing sampled diagnostic detail, source/fix ages, distance, control eligibility and aircraft checks |
| Other diagnostic events | Existing event name and detail: state transitions, control callbacks, read errors/retries, Start/Stop, pause/recovery, connection and lifecycle events |
| log_overflow | droppedEntries since the previous writer report |

Only datagrams from configured `192.168.4.1:5006` count as receiver input. Raw Base64 retains malformed bytes, handshakes and NOFIX messages as well as valid GPS records. Parsed records include rejected duplicate/old packets with accepted=false. No positions are invented for missing packets. For phone mode, callbacks while subscribed are recorded, including rejected mock/non-new callbacks; acceptedBySource is not a claim that downstream aiming validation passed.

LoRa receivedAtMs remains the phone's elapsedRealtime receipt time; senderMs is a transmitter counter, not synchronized wall time. This release does not prove end-to-end measurement age. Phone fixElapsedMs is the Location measurement time. The raw source record and its parsed record are separate enqueues and can straddle a toggle boundary; each independently obeys whether Full Log was enabled when enqueued.

### Minimal files

Existing private files remain `files/aiming-logs/aiming-current.log` and `aiming-previous.log`, capped at 512 KiB each. They record wall/monotonic timestamps and human-readable diagnostic text. They are not automatically copied into public Downloads. The old internal export helper remains for compatibility/tests, but is no longer exposed by the menu.

Retained in both modes: Start/Stop, state transitions, pause/recovery and release outcomes; gaps and sequence boundaries; malformed-data fixed reasons; NOFIX; connection/provider transitions; mode changes; SDK/read failures and timeouts; logging mode and full-storage errors. Routine successful packets, coordinates, command samples, readiness/blocker summaries, repeated authority samples, successful SDK callbacks and routine read/listener traffic are excluded from minimal files.

The filter acts before the existing private asynchronous writer. Number parsing exception messages can contain input text, so these become a fixed Invalid numeric field reason. Other parser messages are fixed descriptions such as Invalid coordinates, No satellites, Invalid HDOP or SNR out of range. Coordinates/raw payloads only reach the full logger. The existing minimal writer's best-effort rotation/overflow behavior remains.

## 4. Missing packets example

Received sequence **1, 2, 3, 7, 8** generates one lora_gap event when 7 is accepted:

```text
lora_gap previous=3 received=7 missing=3 firstMissing=4 lastMissing=6
```

In OFF mode this gap is retained without logging the routine successful packets. In ON mode it also appears in the JSONL diagnostic detail, alongside raw datagrams and parsed packets 1, 2, 3, 7 and 8 with their own timestamps and coordinates. Packet 7 includes missingBefore=3. Packets 4-6 have no coordinates or RSSI/SNR because they were not received.

The gap uses the existing accepted tracker baseline. Duplicates do not recount gaps; rejected data does not advance that baseline. Therefore this identifies holes in the accepted sequence stream, which can include packets received but rejected. It does not prove a particular radio/Wi-Fi loss cause. Wrap uses unsigned 32-bit arithmetic; a missing range can cross zero. Confirmed transmitter restarts generate lora_restart without fabricating a massive gap. No missing count before the first accepted packet or after the final packet is inferred without a later sequence.

## 5. Writer ordering and failure handling

FullSessionLog has one serial executor. Open, data and close operations for each session execute in order. A synchronized active-session reference determines which session receives an event. OFF clears that reference before queuing close, so later events cannot leak into the old file. New ON is blocked until pending control operations settle. Open/close jobs cannot be discarded by data overflow.

Up to 512 data jobs may be pending/running. Further records are dropped without waiting for disk; the session drop count is written in log_overflow on the next write or close and displayed cumulatively in Details. This bounds capture backlog, not total file size. A raw UDP datagram is at most the existing receive-buffer size. No full-file rotation is applied: users manage completed Downloads files.

The writer flushes after each event; normal OFF drains and closes. This is not fsync-per-record or a guarantee against sudden power loss. A storage/open/write/close failure turns Full Log OFF, records a private error, updates Details and posts a Toast. Accepted records still queued for a failed session are not written; the error indicates the file can be incomplete. Logging does not stop or change aiming. Minimal logging remains available when full storage fails.

Control and receiver callbacks do only bounded enqueue/record preparation; JSON serialization, file creation, writes, flushes and close run on the writer. Raw Base64 encoding runs on the receiver worker. There is no flight-control API in the full logger or storage adapter.

```text

     -> FullSessionLog.java: enable() -> serial writer
        -> FullLogStorage.java: open(name) -> public Downloads/CAM3

LoRaTargetLocationSource.java: receive()
  -> FullSessionLog.java: record(lora_datagram, exact Base64)
  -> handle() -> LoRaTelemetry.java: parse / Tracker.accept
     -> full record(lora_packet, coordinates and acceptance)
     -> diagnostic(lora_gap / lora_rejected / lora_restart)
        -> YawAimingController.java: diagnostic()
           -> FullSessionLog.java: record(event, detail) [if ON]
           -> MinimalLogPolicy.java: keep()
              -> AimingDiagnosticLogger.java: event() [if retained]
  -> existing latest-fix publication -> existing aiming inputs (unchanged)

PhoneTargetLocationSource.java: onLocationChanged()
  -> FullSessionLog.java: record(phone_fix)
  -> existing mock/newer checks and fix publication (unchanged)

AimingSession.java: existing diagnostic callback
  -> YawAimingController.java: diagnostic() -> full / minimal routing
YawAimingController.java: sendYaw() -> existing DJI submission
  -> FullSessionLog.java: record(yaw_command)

OFF toggle or YawAimingController.java: pause() after source stop
  -> FullSessionLog.java: disable(reason)
     -> stop accepting new full records
     -> writer drains -> session_end -> flush/close
```
