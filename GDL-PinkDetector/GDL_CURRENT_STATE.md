## Agreed behaviour and code verification

The final agreed v0.15.12.1 scope superseded the proposed v0.15.13 name, X=24% suggestions, and landing-detector/landing-lock proposals. It retained recovery and moved both gestures to X=79.1%, simplified gimbal detection to the red limit, and corrected evidence. | Area | Verified in current code |
| --- | --- |
| Main loop | `GdlAccessibilityService.captureLoop` calls `captureIfReady()`, then reschedules using `currentCaptureIntervalMs()`. Screenshot processing routes through `processScreenshot()` to the relevant detector/coordinator. |
| Gesture coordinates | `GimbalKnobDetector`: `FIXED_X=0.791f`, `GESTURE_START_X=FIXED_X`, `GESTURE_START_Y=0.45f`, `DRAG_BOTTOM_Y=0.79f`. Both `processGimbalTest()` and `processProductionGimbalRecovery()` multiply these by screenshot dimensions and call `dispatchGimbalDrag()` with equal start/end X. |
| Touch implementation | `dispatchHoldThenDrag()` dispatches a stationary 2-second stroke with continuation enabled, then `continueStroke()` for a 6-second downward path. This represents one continued pointer across **two dispatch calls**, not a second pointer at a white-ring location. `mapSourcePointToView()` scales screenshot coordinates to overlay dimensions. Actual device mapping remains unmeasured here. |
| Test start/stop | Normal readiness delay is 3 seconds; gimbal test then has a guard-dependent 10-second countdown. Red is evaluated before countdown/in-flight/rest branches. Two positive red evaluations latch completion; a negative evaluation resets the count. About 13 seconds to first hold is conditional on guards/capture scheduling, not a guaranteed start time. |
| Retry | 6-second rest after the gesture callback; repeated down-only gestures until red confirmation. No white/green knob or dashed-line visibility prerequisite. No attempt ceiling in these recovery loops. Completion prevents further gestures; already dispatched movement is not explicitly cancelled by red detection. |
| Production arming | Starts disarmed on a new run. Successful real-tap completion with `isValidatedGreenPlusWithPink()` arms recovery; ActiveTrack success is not the arming event. Default recovery is On for `COMBINED_REAL`, Off for standalone `PRODUCTION`, with a configurable 15-second no-selected-target timeout. A no-pink selection does not meet the arming predicate. |
| Production coordination | `processCombinedReacquire()` evaluates no-target timeout in post-cycle waiting too. `gimbalGestureAllowed()` permits combined recovery outside `ACTIVE_TRACK`, including `COMPLETE`/S11. Active recovery takes priority over green-plus evaluation; after red confirmation it resumes searching once an in-flight gesture finishes. |
| Red detector | `GimbalKnobDetector.evaluate()` downsizes to at most 720px width, searches near X=79.1%, accepts compact red components centred in Y=72–84%, with a 2% vertical search margin. It classifies pixels, not a numerical angle from DJI telemetry. |
| Evidence | `GimbalEvidenceAnnotator` draws on a copied bitmap: red limit region, detected red knob, and cyan **requested** path when supplied. No full-height blue search rectangle. These annotation pixels do not dispatch touches or feed detection. |
| Guard limitations | Gimbal dispatch checks readiness, allowed preset/state, DJI foreground, mandatory full-screen setting, Android 11+, and the full-screen guard. There is no landing/RTH recognition or landing lock. Guard checking before the hold does not establish safety throughout the continued drag. |
| Settings/evidence | Combined defaults include 400ms search, 800ms plus retry, 120ms tap, minimum 8 pink pixels. Each run gets a settings snapshot and timestamped evidence folder. Hard-save saves successful captures, not guaranteed frames at every scheduled tick. |
| Telemetry | `scheduleTelemetryRead()` runs asynchronously at roughly 1-second intervals; filename creation reads `latestTelemetry` separately. Altitude/distance suffixes can be stale or differ between RAW/ANNOTATED images for one frame. They are not latitude or flight-state input. |

Existing green-plus/pink and ActiveTrack behaviour was intended to remain unchanged by the lane correction; historical byte-for-byte equivalence to old ZIPs was not established in this review. See `ReacquirePipeline.kt`, the plus/pink detectors, `ActiveTrackPanelDetector.kt`, and the existing project documentation before changing those features.

None independently proves physical gimbal movement. Production outcome handling can occur between red evaluations, so “two consecutive frames” is more precisely two positive detector evaluations without an intervening negative evaluation.
